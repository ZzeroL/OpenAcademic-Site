01仓库与分支

主仓在 Gitee，GitHub 收口同步。两边内容一致，不维护分叉。日常开发在功能分支，main 保持可发布。

分支用途合并方式
main可发布版本只接受 PR / MR
feat/*新能力合并后删除
fix/*缺陷修复合并后删除
chore/*构建、依赖、文档合并后删除

不直接在 main 上提交，不用 force push 覆盖他人分支。若发现冲突，先 rebase 自己的分支，而不是重置主分支。

02提交规范

提交信息写「为什么」，不写「改了什么」——改了什么，diff 里都有。

commit style
feat(scan): 候选按领域 + 周 + 标识去重
fix(agent): 工具失败时保留原始状态
docs(deploy): 补旧版 IPAPER_ 升级路径
chore(ci): 增加前端 typecheck 门禁
  • 类型：feat / fix / docs / chore / refactor / test。
  • 范围：模块名，如 scan、agent、deploy。
  • 正文：必要时写影响面、迁移、验证方式；不要贴大段日志。
  • 一个提交一件事：格式化与功能改动分开，便于回滚。

03PR 检查清单

提交 PR 前逐项确认。检查清单不是形式，是防止「看起来能用」的改动进入 main。

  • 测试通过
  • lint / typecheck 通过
  • 前端构建通过
  • 迁移影响面已评估
  • 失败状态可见
  • 文档已同步
  • 无敏感信息
  • 回滚路径清晰
重点看什么

涉及判断、出处、通道回执的改动，必须说明「失败时界面显示什么」。只写成功路径的 PR，默认还没完成。

不跳过 hooks，不用 --no-verify 绕过检查。如果 hook 失败，修根因，不修提示。

04测试

pytest 覆盖记忆层、领域容器、上下文回收、工作区模型、引句契约、通道与 PDF 读取。前端目前以构建与人工验证为主。

优先补测

容易静默失败的地方

  • crypto_utils 往返与 mask
  • load_model_config 合并优先级
  • AgentState.update_todos 终止路径
  • run_agent_stream 事件序列
  • 多会话并发与断连续跑
人工验证

只能真机跑

  • 多用户隔离
  • PDF 真样本页眉过滤
  • 领域 IA 23 条路由
  • 一次真机精读端到端

测试债的完整清单见已知限制与规划。

05前端构建与 CI

CI 跑在 GitHub Actions；主仓在 Gitee，因此需要镜像或自建 runner。前端产物由 CI 出包，服务器只跑产物。

01检查lock 文件、lint、typecheck、测试。
→
02构建前端产物打包，记录 commit sha。
→
03发布上传产物，服务器按 sha 切换。
→
04验证健康检查；失败可回滚。

依赖必须锁版本。不在服务器上 npm install，也不在 CI 里跑会改写 lock 文件的命令。

06发版与双仓同步

  1. 功能分支合入 main，等待检查全绿。
  2. 在 Gitee 打 tag；同步到 GitHub，保持两边 commit 一致。
  3. CI 出前端包；按服务器部署与升级发布。
  4. 发布说明写：迁移、配置变更、回滚注意、验证结果；同时同步 CHANGELOG.md 的版本段与已知限制。

双仓同步优先用 git push --mirror 或等价方式，不手工复制文件。若出现分叉，先对齐再发布，不要在两个远端各改一版。

07常见返工与避免方式

返工根因避免
功能「完成」但没有状态落点只做了界面先写数据契约，再做视图
失败路径没人测只验证成功案例PR 必须写失败时显示什么
升级覆盖旧目录图省事新目录并行 + 健康检查 + 切流
双仓分叉手工复制镜像同步，发布前对齐

返工不可怕，怕的是返工之后没有更新检查清单。每次线上问题都应该变成一条可执行的检查项。
