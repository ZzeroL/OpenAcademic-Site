01建模原则：判断是主表

很多学术工具把论文当主表，判断是笔记的附属。OpenAcademic 反过来：判断是主表，论文是依据。一条判断可以引用多篇论文的多个节，但一条判断只有一个当前状态。

DOMAIN领域归属维度，不是文件夹。
→
ITEM判断主表；带状态与出处。
→
EVIDENCE依据论文 + 节锚点 + 引句。
→
TRAJECTORY轨迹append-only 变更日志。

这条原则决定了几件事：删除论文不能级联删除判断；判断的状态变更必须写轨迹；论文元数据可以刷新，判断的出处快照要保留。

02核心表

以下是逻辑表名与职责，物理表名、字段类型与索引以仓库迁移为准。

表职责关键字段（逻辑）写入方
domains领域与归属id、name、owner_id、status管理员 / 工作区
papers论文元数据与文件arxiv_id、doi、openalex_id、title、pdf_path、section_map扫描 / 工具
items判断主表id、domain_id、claim、status、paper_id、section、quote、locator_stateagent / 人
decisions本周决定id、week、text、status、evidence_item_idsagent 起草 / 人裁决
tasks派活与运行状态id、domain_id、prompt、status、created_by、last_step人 / runner
trajectory_events判断变更日志id、item_id、action、reason、actor、created_at只追加
channel_runs通道运行回执id、channel、domain_id、week、status、hits、error扫描
scan_candidates扫描候选池domain_id、week、identifier、state、dispatched_task_id扫描 / 派活
notes笔记与索引id、domain_id、body、embedding_ref、links人 / agent
出处快照

items 上的 section 与 quote 是判断发表时的快照，不随论文版本静默更新。论文换版后，应显式标记「出处需复核」，而不是自动覆盖。

03一条判断的字段

字段含义约束
claim判断本身，一句话不写过程，不写「本文认为」
status候选 / 确认 / 推翻 / 搁置只能经裁决或轨迹变更
paper_id主依据论文可空；空时显示「未定位」
section / quote节锚点与引句发表时快照；不做自动补全
locator_state已定位 / 未定位 / 需复核未定位不可直接引用
domain_id归属领域不可为空；跨领域用多条目
owner_id起草者agent 或人，均可审计

字段设计里没有「置信度」。置信度不能替代人裁决，反而会让候选态看起来像已定稿。不确定性通过 locator_state 与候选状态表达。

04归属字段与只读视图

界面不直接拼装表，而是读视图。当前有三类只读视图：

v_week_digest

本周清单

判断、粗筛未读、候选与通道异常汇总；按领域 + 周聚合。

v_domain_items

领域条目流

判断 + 出处 + 当前状态；只包含未逻辑删除的条目。

v_channel_health

通道健康

每条通道最近一次运行状态、错误与下周是否重跑。

归属字段统一用 domain_id 与 owner_id。多用户隔离靠 owner_id 与领域成员关系，而不是在前端过滤。视图里不要出现跨用户聚合，除非显式标注为管理员视图。

05逻辑删除与迁移

  • 逻辑删除：deleted_at 非空即视为删除；视图过滤，轨迹轴不删除。
  • 论文删除：不级联删除判断；判断保留出处快照，标记「依据已移除」。
  • 状态回退：不直接改 status；写一条轨迹事件，再由事件派生当前状态。
  • 迁移：只增不删字段；旧字段保留读兼容，写路径先切新字段。
迁移影响面

改 items 或 channel_runs 的字段时，至少检查：工作区视图、清单聚合、扫描去重键、轨迹轴回放、pytest 里的工作区模型测试。任何一项没有覆盖，就不要合。

06改动前的检查清单

  1. 新字段是否有明确的写入方与读取方？没有读取方的字段不加。
  2. 新状态是否需要在界面可见？如果需要，它落在哪个视图？
  3. 删除或合并是否破坏轨迹轴的可解释性？
  4. 是否改变了候选去重键？跨周已派候选会不会重新入库？
  5. 多用户隔离是否仍然成立？

这五条来自实际缺口：候选跨周重复、状态无落点、轨迹无法回放，都会让「可核对」失效。

07怎么扩展

扩展数据模型时，优先加事件而不是加状态字段。事件可以回放，状态字段只能覆盖。只有当查询性能确实需要时，才从事件派生冗余字段，并保证它可以重建。

能重建的，才允许冗余；不能重建的，必须保留原事件。
