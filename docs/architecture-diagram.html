    01系统上下文：谁在用，连了什么

    OpenAcademic 是一个单机可自部署的研究生产线。系统边界内是 Agent、工作区数据与界面；边界外只有三类依赖：模型端点、arXiv 全文、OpenAlex 引用。

    ACTOR研究者 / 组内成员交一句话、确认判断、开组会、勾四态。
    ↓
    SYSTEMOpenAcademic收件箱、清单、领域条目、扫描通道、Agent 内核。
    ↓
    EXTERNALOpenAI 兼容端点 · arXiv · OpenAlex推理、全文与引用；对不上会显式上清单，不猜。

    没有账号体系之外的 SaaS 依赖，没有外部消息队列，没有托管数据库。数据根在 <repo>/.openacademic/，生产环境用 OPENACADEMIC_HOME 指到代码目录之外。

    02容器：五个运行单元

    容器职责技术不做什么
    Web收件箱、清单、领域工作台Next.js 16 + CopilotKit不直接访问模型或数据库
    Backend登录、会话归属、SSE、工作区路由FastAPI不实现 Agent 循环
    Core单轮循环、工具、记忆、扫描Python 包不反向依赖 backend
    Storage关系数据、向量索引、论文文件SQLite + Chroma + 目录不做外部同步
    Runner启动、建库、播种管理员start.mjs不在服务器上编译前端

    CLI 是 Core 的第二种外壳，和 Web 共用工具、记忆与上下文管理。它不经过 Backend，因此可以作为最小可验证路径：当 Web 出问题时，CLI 仍能证明内核是否正常。

    03组件：Agent 单轮里有什么

    01 · LOOP

    单轮循环

    组装上下文 → 模型决策 → 工具调用 → 结果回填 → 压缩/限流 → 继续或收尾。主循环 40 轮。

    02 · REGISTRY

    工具注册表

    27 个绑定；模型只见注册表。需要审批的工具单独走 HITL，run_bash 不在表内。

    03 · MEMORY

    三层记忆

    笔记检索、论文元数据、当前上下文。压缩按「可重取性」排序。

    04 · SCAN

    扫描通道

    关键词、前向引用、后向引用；每次运行写 channel_runs。

    05 · HITL

    审批层

    请求、批准、拒绝、超时都有事件；拒绝理由回填给模型。

    06 · TRAJECTORY

    轨迹轴

    判断的起草、确认、推翻、搁置 append-only；理由必填。

    组件之间通过显式的数据结构连接，而不是共享可变全局状态。这让「一次任务停在哪」可以从事件与表里复原。

    04记忆与数据模型

    从外部看，只需要记住四组数据：论文、判断、任务、运行回执。领域是它们的归属维度，轨迹轴是判断的变更日志。

    INPUT任务tasks + 队列；重启恢复 queued。
    →
    SOURCE论文arXiv 元数据、PDF、节边界。
    →
    JUDGMENT判断items + 候选态 + 出处。
    →
    CHANGE轨迹append-only，理由必填。
    →
    RECEIPT回执channel_runs + scan_candidates。

    字段、索引与只读视图见工作区数据模型；候选去重见候选落表与一键派活。

    05部署拓扑

    EDGENginxTLS、反代、静态产物。
    ↓
    APPsystemd: frontend / backend前端只跑 CI 产物；后端跑 FastAPI。
    ↓
    DATAOPENACADEMIC_HOMESQLite、Chroma、论文文件、.secret_key。
    ↓
    CIGitHub Actions出前端包，服务器下载后切换 release。

    服务器上不编译前端，是为了让发布与构建解耦：回滚只需切目录，不需要重新装依赖。停机与回滚步骤见服务器部署与升级。

    06一次派活的请求时序

    以「读 LooGLE 那篇，出节级笔记」为例，一次成功请求大致经过：

    1. Web 提交一句话与领域，调用 Backend 的任务接口。
    2. Backend 写入 tasks，返回任务 ID；此时前端可以刷新或离开。
    3. Runner 从队列取出任务，启动 core 的 Agent 循环。
    4. Core 调 get_papers 检索，paper_pdf_download 下载，read_paper_section 按节读。
    5. Core 经 save_item 写入候选判断；轨迹轴记录起草事件。
    6. Backend 通过 SSE 推进度事件；任务完成，状态变为待验。
    7. Web 收件箱三列看板刷新，出现「条目 × 4 · 待验」。
    关键点

    第 2 步之后，任务就不再依赖浏览器连接。断线只影响界面刷新，不影响执行；这也是「不是聊天框」在架构上的体现。

    07怎么读这些图

    先看依赖方向，再看状态落点，最后看失败路径。一个组件如果既不写状态、也不影响失败可见性，它多半不承重。

    • 上下文图 回答「边界在哪」
    • 容器图 回答「部署什么」
    • 组件图 回答「循环怎么转」
    • 时序图 回答「断线怎么办」
