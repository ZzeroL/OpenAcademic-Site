    01限流三层

    限流不是单点配置，而是三层预算。每层解决不同的问题：入口防挤占、循环防无限试错、工具防外部接口被打爆。

    层限制什么超限后的行为
    入口层同时运行的任务数与单用户并发新任务留在 queued，不丢、不静默拒绝
    循环层主循环 40 轮、子代理 20 轮停在待验，附最后一步与未完成原因
    工具层单工具重试与外部接口节流记失败并回填；连续无进展则收尾

    三层限流的共同目标是把任务送到一个可解释的终点，而不是让它无声地消失。排队中的任务可见，超轮数的任务可见，工具失败也可见。

    参数口径

    具体阈值以仓库配置为准；本页只描述分层与超限行为。调整参数不应改变「超限必须留下状态」这条约束。

    02上下文分层压缩

    上下文窗口 128K。70% 与 90% 是两档阈值，不是两个开关：

    70% · FOLD

    折叠早期工具结果

    保留结论、出处与关键引句；把完整 PDF 段落替换为可重新读取的引用。目标是释放空间但不丢证据。

    90% · FORCE

    强制压缩并丢弃中间产物

    可重新获取的下载内容、重复的搜索结果直接丢弃；判断、节锚点与引句不能丢。丢不起就失败。

    压缩按「可重取性」排序，而不是按消息新旧排序。一条很旧的判断比一份刚下载的 PDF 更值得保留，因为后者可以再取一次，前者一旦丢了就只剩模型的记忆。

    禁止项

    不得在压缩时「顺手补全」节号或引句。压缩只能缩短依据，不能生成依据；无法保留出处时，应显式标记未定位。

    03工具结果策略

    工具返回的内容分三类处理：

    • 可读结果（检索命中、节文本）按长度截断，保留首尾与命中段落。
    • 大对象（PDF、图表、LaTeX 源码）落盘，上下文只放路径与摘要。
    • 状态结果（成功 / 失败 / 跳过）必须结构化，不能被当成自然语言文本随意改写。

    结构化状态是失败可见性的基础。如果工具失败被模型改写成「没有找到相关内容」，人看到的就是一次正常的空结果——这比失败更糟。

    状态回执 · 示意channel_runs

    openalex_backward 本周未完成：OpenAlex 返回 429，通道记 skip，清单照常交付。

    status = skipretry = next_weekreceipt = 可见

    失败不是「清单里少几条」，而是「清单里明确写着哪条没跑」。

    04HITL 审批

    人机协同审批只用于「模型不该自己决定」的动作。当前最典型的是 run_bash：它存在，但不注册进模型工具表，只能经审批层触发。

    01请求模型提出需要执行的动作与理由。
    →
    02挂起任务进入等待，界面显示待审批。
    →
    03裁决批准 / 拒绝 / 超时。
    →
    04回填结果或拒绝理由回到上下文。

    审批不是「确认弹窗」，而是任务状态的一部分：挂起期间不能继续其他工具调用，避免模型在等待时绕路执行。拒绝理由必须可读，否则模型只会重复请求。

    05失败可见性矩阵

    哪些失败必须上界面，哪些可以只留在日志里，按「人是否需要据此改动作」判断。

    失败状态落点界面可见人应该做什么
    通道 429 / 超时channel_runs.status是下周重跑，或换源
    PDF 缺页 / 节边界异常工具结果 + 判断标记是换版本或人工核对
    引句定位失败「未定位」是不可直接引用
    任务超轮数待验 + 最后一步是拆小任务重派
    单次工具重试工具轨迹否无需动作
    内部调试日志日志文件否无需动作

    注意最后两行：不是所有失败都要打扰人。可见性的门槛是「它是否改变判断或下一步动作」。

    06可恢复性

    系统假设进程会重启、连接会断、浏览器会关。恢复策略按状态区分：

    • queued：重启后自动恢复，重新入队。
    • running：标记为中断，不自动重跑；等人确认后重新派活，避免重复写入判断。
    • awaiting_review：保持不变，继续待在待验列。
    • done：不回滚；如需修改，走推翻与再确认。

    不自动重跑 running 是一个产品决定：重复执行可能产生重复候选，破坏「判断的变更日志」。宁可让人多点一次，也不让轨迹出现无法解释的分叉。

    07回执、轨迹与观测

    三类记录构成可观测性：

    记录回答的问题粒度
    channel_runs这周哪条通道跑了、哪条没跑、为什么每次运行
    工具轨迹这一步用了什么、返回了什么每次调用
    轨迹轴这条判断为什么确认或推翻每次变更

    它们共同支撑「漏检可归因」。没有这三类记录，系统只能证明自己输出了什么，不能证明自己没读到什么。

    可靠性判据

    一次失败之后，人能否在界面上回答三个问题：哪一步失败、失败影响了什么、下一步该做什么。能回答，失败就是可控的。
