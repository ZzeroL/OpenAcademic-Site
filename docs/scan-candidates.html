01三条通道各管什么

通道抓什么数据源典型失败
关键词组里已有叫法的新论文arXiv，按领域关键词 + 本周 submittedDate 窗口限流、查询超时
引用链 · 前向本周谁引了种子论文OpenAlex429、标识对不上
引用链 · 后向种子引了谁，哪些该读却没读OpenAlex429、引用列表不完整

关键词抓「叫法」，引用链抓「邻近」。只有关键词会漏掉换了术语的同主题工作；只有引用链会漏掉尚未被引用的新预印本。两条路互为补集，不是冗余。

02周窗口：先定周，再定范围

扫描以「领域 + 周」为单位运行。周窗口决定三件事：关键词通道的 submittedDate 范围、前向引用只看本周新增、后向引用只对本周种子跑。

  • 周起点固定，避免不同人看到不同的「本周」。
  • 跨周不补扫：上周没跑的通道记 skip，本周重新开始，不追溯填数。
  • 已派候选跨周不再入库：派过的标识在后续周直接跳过，避免重复消耗阅读预算。
为什么按周而不是实时

研究阅读的节奏是周，不是秒。按周聚合让「本周清单」有稳定边界，也让通道失败可以在下周被显式重跑，而不是在实时流里被淹没。

03候选键与去重

候选去重键是 领域 + 周 + 标识。标识优先用稳定 ID，而不是标题：

KEYdomain_id同一论文可属于多个领域。
+
KEYweek周窗口。
+
KEYidentifierarXiv id 优先，其次 DOI / OpenAlex id。

同一篇论文在同一周、同一领域只会有一条候选。不同通道同时命中时，合并来源而不是建两条；来源字段保留 keyword / forward / backward 以便解释「为什么它会出现」。

标题不是键

预印本改标题很常见。用标题做去重键会把同一篇论文识别成两篇，也会把不同论文合并。标题只用于展示与兜底对齐，不进入候选键。

04落表与状态

scan_candidates 的逻辑状态很少，刻意保持简单：

状态含义下一步
new本周新落池，未派等人一键派活，或留在池里
dispatched已生成任务关联 task_id，等待阅读结果
ignored人决定不读记录理由，跨周不再入库

候选不是判断，不进入 items。只有精读后经 save_item 发表的判断才进入领域条目流。这条边界防止「扫到就算知道」。

05一键派活只给清单

「派给 agent」不预设阅读顺序，也不替 agent 选题。它只把候选清单交出去：

系统负责

给清单

候选 ID、标题、来源通道、领域、周；已派与未派数量。

agent 负责

定顺序

先读哪篇、要不要合读、粗筛还是精读；按任务目标自行决定。

这与「人只做四个动作」一致：人决定要不要读这一批，agent 决定怎么读。如果系统硬编码阅读顺序，agent 就无法根据已有判断调整优先级。

候选卡 · 示意15 篇 · 已派 6

扫描候选共 15 篇，未派 9 篇；按领域 + 周 + 标识去重，派过的跨周不再入库。

06通道失败怎么落

每条通道每次运行都写一条 channel_runs，状态三选一：

OK

正常完成

记录命中数；0 命中也是成功，不代表没有新论文。

SKIP

主动跳过

429、限流或明确不跑；清单显示「下次再跑」。

FAIL

失败

超时、解析错误、数据源不可用；附错误摘要。

网络失败不回 5xx，不影响清单生成。清单照常交付，只是把「哪条通道没跑」写出来。这条设计与「漏检可归因」直接相关：安静地少几条，比明确地失败更危险。

07口径与运维

  • 命中数是通道返回并落池的数量，不是去重后数量；去重后数量单独展示。
  • 已派以 dispatched 状态为准；任务失败不自动回到 new，需要人工决定。
  • 跨周不回溯补扫；历史周的数字不因本周重跑而改变。
  • 候选池清理不做定时删除；ignored 保留理由，供后续解释「为什么没读」。
