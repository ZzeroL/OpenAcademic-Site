为什么是「等它干」，
不是助手。

助手回答一个问题，生产线交回一批可核对的判断。OpenAcademic 把「读过并真的知道」拆成可验证的交付物、可归因的漏检和 append-only 的轨迹——这三件事决定了它为什么存在。

    01定位：交付物不是聊天记录

    大多数科研助手优化的是「这一轮答得像不像」。OpenAcademic 优化的是「一周之后，这条结论还在不在、敢不敢拿去用」。

    所以它不以对话为中心，而以收件箱为中心：你登录后先看到的是状态线、待确认的决定、三列看板与本周清单。聊天只是派活的一种入口，不是最终产物。

    02三个判断：交付物、漏检、轨迹

    产品里所有取舍都可以回溯到三句话。它们不是价值主张，是验收标准。

    01 · DELIVERABLE

    交付物是判断，不是操作

    判断可以进稿子、进幻灯片、进组会讨论；操作只说明「我点过这个按钮」。

    02 · ATTRIBUTION

    漏检必须可归因

    没扫到、通道失败、扫到没派、派了没读——每一种都要在清单里留下痕迹。

    03 · TRAJECTORY

    判断的变更必须留痕

    起草、确认、推翻、搁置都写进 append-only 的轨迹轴，理由不能省。

    为什么漏检比错检更危险

    错检会在核对时暴露，漏检不会。一篇该读的论文没进候选池，组里没有人会知道它存在。因此产品不承诺「完美召回」，而是承诺每条通道跑了什么、哪里没跑、为什么没命中，都写进本周清单。三通道的设计、skip / fail 回执与候选池去重，都是为这一条服务的。

    为什么轨迹轴是承重墙

    模型会变、prompt 会改、论文会被新版本替换。如果判断只是一次写入，半年后无法解释「当时为什么这么判」。轨迹轴保存的是判断的变更日志：谁在什么依据上起草，谁确认，谁推翻，理由是什么。它让「读过的结论」从一次性输出变成可审计的资产。

    素材层的错误没人能发现，所以错了必须看得见。

    03为什么不做「更聪明的助手」

    更聪明的助手仍然把认知负担留在人身上：你得知道该问什么、怎么追问、答案可不可信。OpenAcademic 反过来，把人的动作压缩到四个：交一句话、确认或推翻、开组会、勾四态。

    能力聊天助手OpenAcademic
    入口对话框，等人想清楚问题收件箱，状态先于问题
    过程一轮轮追问，过程不可见三列看板 + 工具轨迹，进行中可见
    结果文本，随手复制走领域条目，带 ID / 节锚点 / 引句
    纠错重新提问确认 / 推翻 / 搁置，理由入轨迹轴
    漏检无法回答「你没读什么」通道回执 + 粗筛未读 + 候选池
    复用依赖上下文窗口判断落库，跨周、跨会话存在

    这也是为什么产品不做「对话里直接建领域」「删除论文的 UI 入口」「会议纪要与 PPT 生成」。这些不是欠债，是边界：每加一个入口，都会稀释「判断—出处—轨迹」这条主链。

    04一条判断的完整生命周期

    从一句话到一条可引用的判断，会经过六个状态。每个状态都有明确的归属与可见性。

    01派活一句话 + 领域，落 tasks，进队列。
    →
    02扫描三通道按周跑，候选落池并去重。
    →
    03精读按节读原文，工具轨迹可见。
    →
    04发表save_item 写入候选态。
    →
    05裁决人确认 / 推翻 / 搁置，理由入轴。
    →
    06复用交付本周清单，进稿子与组会。

    注意第 4 步：agent 只能「发表」判断，不能「定稿」判断。候选态是产品里最重要的权限边界——它把模型的不确定性留在人能看见的位置，而不是靠置信度分数藏在后台。

    设计后果

    如果一条判断没有出处，它应该显示「未定位」，而不是补一个像样的节号。如果一条通道挂了，它应该记 skip 或 fail，而不是让清单看起来完整。产品的可信度来自这些不体面的状态被保留下来。

    05亮点定位：它到底强在哪

    面向访客的一句话版本：派方向，它自己扫通道、持续读、持续比对、持续记；你收回来的不是聊天记录，而是能直接进稿子的结论。展开成四条可验证的差异：

    01 · EVIDENCE

    每条结论追得到原文

    ID + 节锚点 + 引句三件套；定位不到就显式标记，禁止编造节号或引句。

    02 · COVERAGE

    没读到的东西也看得见

    关键词 + OpenAlex 前向 / 后向三条通道；粗筛未读附一句不读的理由。

    03 · CHANGE

    判断变更可追溯

    轨迹轴 append-only；推翻必须写理由，理由先由 agent 起草，人只改。

    04 · OWNERSHIP

    数据留在自己机器上

    Apache-2.0，自部署；论文、笔记与判断都在工作区目录，不依赖外部服务。

    06刻意不做的边界

    产品的可信度不仅来自做了什么，也来自明确不做什么。以下方向已对齐为「不做」，提 PR 前需要先推翻这份共识，而不是顺手加上。

    • 每人自带 API Key（BYOK）
    • 登录改 JWT
    • 对话里直接建领域
    • 删除论文的 UI 入口
    • run_bash 进模型工具表
    • 统计持久化与历史回溯
    • 会议纪要 / PPT / 外部日历
    • 无界 todo 硬拒

    判断标准只有一条：它是否强化「判断—出处—轨迹」主链。强化则做，稀释则不做；与模型是否更强无关。

    常见误读

    「不做」不等于「永远不会做」，而是「不在当前产品边界内」。如果要把其中一项纳入，需要同时说明它如何不破坏交付物的可核对性，以及轨迹轴如何记录它带来的新状态。

    07读完这篇，带走什么

    如果你只记三件事：

    1. 交付物是判断。没有 ID、节锚点与引句的文本，不算产品输出。
    2. 漏检要可归因。通道回执、粗筛未读、候选池去重，比「召回率」更能说明系统是否可信。
    3. 轨迹轴是承重墙。判断的变更日志让半年后的你能解释当时的决定。

    接下来建议按顺序读：系统架构看机制，一周流程看人怎么用，路线图看现在缺什么。三篇读完，后面的数据与工程文档才知道该往哪看。
