    01部署形态与前置

    生产形态是单机、多用户、自部署：Nginx 在最前，两个 systemd 服务（前端与后端），数据放在代码目录之外。没有外部数据库、消息队列或对象存储。

    组件要求说明
    Python≥ 3.10后端与 Agent 内核
    Node.js≥ 20.9前端构建与 start.mjs
    模型端点OpenAI 兼容MODEL_NAME / MODEL_URL / MODEL_API_KEY
    网络可访问 arXiv / OpenAlex引用链与外链下载
    存储本地磁盘SQLite、Chroma、论文文件

    Windows 下激活虚拟环境用 .venv\Scripts\activate，其余命令相同。GitHub 镜像：https://github.com/ZzeroL/OpenAcademic.git；主仓在 Gitee。

    02本地启动

    quickstart · bash
    $ git clone https://github.com/ZzeroL/OpenAcademic.git
$ cd OpenAcademic && python -m venv .venv
$ source .venv/bin/activate && pip install -e .
$ cd frontend && npm ci && cd ..
$ cp .env.example .env   # 填 MODEL_NAME / URL / API_KEY
$ node start.mjs
✓ ready → http://localhost:3000

    首次启动才会初始化：建工作区 → 播种技能 → 建库 → 插入管理员。clone 本身不建库、不建工作区、不写任何配置。

    第一件事：改密

    初始管理员 admin@example.com / admin123 公开写在源码里，等同无口令。登录后立即改密，再给组员开账号。没有注册入口，账号由管理员创建。

    03生产目录与环境变量

    生产环境把数据根移出代码目录：

    变量用途注意
    OPENACADEMIC_HOME数据根目录SQLite、Chroma、论文文件、密钥
    MODEL_NAME模型名与端点一致
    MODEL_URLOpenAI 兼容端点不要带多余路径
    MODEL_API_KEY密钥由 .secret_key 加密存储

    .secret_key 是解密已存 API Key 的唯一钥匙。备份它，不要重新生成；重生成等于让所有已存密钥失效。

    目录结构

    建议 /srv/openacademic/data 放数据，/srv/openacademic/app 放代码，/srv/openacademic/releases 放前端产物。升级时只换 app 与 releases，不动 data。

    04systemd 与 Nginx

    两个 unit：一个跑后端，一个跑前端产物。按模板安装后开启自启。

    server · systemctl
    $ sudo systemctl enable --now openacademic-backend
$ sudo systemctl enable --now openacademic-frontend
$ sudo systemctl status openacademic-backend --no-pager

    Nginx 负责 TLS、反代与静态产物。后端只监听本机端口，不直接对公网暴露。上传大小、超时与 SSE 的缓冲需要按实际调整，尤其是长任务事件流。

    SSE 注意

    反向代理默认可能缓冲事件流，导致界面进度延迟。需要关闭对应路径的代理缓冲，并给足读超时；否则任务在跑，页面看起来像卡住。

    05前端产物：发布与回滚

    前端由 CI 出包，服务器下载后切换 release，不在服务器上编译。

    deploy.sh · server
    $ ./deploy.sh startall
$ ./deploy.sh release /tmp/frontend.tar.gz <sha>
$ ./deploy.sh health   all ok
$ ./deploy.sh status
$ ./deploy.sh rollback
    • 发布：解包到新的 release 目录，切换符号链接，重载前端服务。
    • 健康检查：后端健康接口 + 前端首页 + 关键 API。
    • 回滚：切回上一个 release；数据与后端代码不回滚，除非同版本发布说明要求。

    发布顺序建议：后端兼容改动 → 前端产物 → 配置变更。先让旧前端能跑新后端，再切前端，回滚窗口最小。

    06从旧版升级

    旧版使用 IPAPER_ 前缀。升级不是覆盖安装，而是新目录并行：

    1. 代码放到新目录，不要覆盖旧目录。
    2. .env 里的 IPAPER_ 改成 OPENACADEMIC_。
    3. .secret_key 原样复制，不重新生成。
    4. 指向同一数据目录，先启动新版做健康检查。
    5. 确认无误后切 Nginx upstream，再停旧服务。
    不要做的事

    不要删除旧目录作为「清理」；不要在未备份 .secret_key 的情况下重装；不要在数据目录里直接跑迁移而不先备份。

    停机与回滚需要按发布说明逐条执行。若没有发布说明，按「新目录 + 同数据 + 健康检查 + 切流」的最小路径操作。

    07上线前安全清单

    项当前上线要求
    管理员口令公开默认值立即修改
    HTTPSNginx 可配强制跳转
    Cookie Secure未设置开启
    会话令牌明文存储哈希存储
    配置密文AES-CBC 无 MACAES-GCM / HMAC
    CORS全开收窄到域名
    登录节流无失败次数限制
    账号开通管理员建号保持

    内部小团队可以先跑；对公网开放前，这张表里的 wip 项必须处理。

    08故障排查顺序

    1. 看服务：systemctl status 两个 unit 是否都在跑。
    2. 看健康：./deploy.sh health 是否通过；后端能否读数据目录。
    3. 看日志：后端日志里找任务 ID、工具失败与通道状态，不只 grep 500。
    4. 看 SSE：界面卡住但任务在跑，优先查 Nginx 缓冲与超时。
    5. 看磁盘：论文文件与 Chroma 索引增长；空间不足会先表现为写入失败。
    6. 看密钥：模型调用失败且日志提示解密错误，检查 .secret_key 是否被替换。
    排查原则

    先确认「失败发生在哪一层」，再决定重启什么。盲目重启会丢掉正在运行的任务上下文，让问题更难复现。
