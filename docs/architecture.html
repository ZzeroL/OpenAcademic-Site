ARCHITECTURE · 02

它怎么跑，
怎么不跑飞。

一个 Agent 内核，两种外壳。单轮循环负责「下一步做什么」，工具注册表负责「能做什么」，三层记忆与两档压缩负责「还记得什么」，HITL 审批负责「哪些不能自己干」。

01总览：一个内核，两种外壳

CLI 与 Web 不是两套实现，而是同一套 core 的两个入口。工具、记忆、上下文管理、扫描通道都在 core；backend 只做会话、鉴权、事件流与工作区路由。依赖方向是硬约束：

SHELLWeb / Next.js · CLI收件箱、清单、领域工作台、命令行。
↓
BACKENDFastAPI + SSE登录、会话归属、右栏进度、AG-UI 事件流。
↓
COREAgent 循环 · 工具 · 记忆 · 扫描不反向依赖 backend，可在 CLI 里单独跑。
↓
STORAGESQLite + Chroma + 工作区目录论文、判断、任务、通道回执与向量索引。

这条依赖方向决定了两件事：CLI 可以先于 Web 验证能力；Web 的页面状态必须来自后端契约，而不是前端自己编。前端切换路由不丢操作，也依赖同一份工作区状态。

02请求怎么进来

一次「派出去」不是直接调用模型，而是先落任务、再进队列。这样刷新、断线、重启都不会把活弄丢。

01提交一句话 + 领域，写 tasks。
→
02排队进程内队列；queued 重启可恢复。
→
03运行Agent 循环消费任务，SSE 推事件。
→
04回写判断候选态、工具轨迹与任务状态。
→
05待验收件箱三列看板等人裁决。

队列是进程内的，不是分布式消息系统。这是刻意的：单机、小团队、可解释优先。代价是水平扩展需要重新设计，收益是没有额外基础设施要维护。

03单轮循环：模型决定下一步

每一轮都做同一件事：组装上下文 → 模型决策 → 执行一个或多个工具 → 回填结果 → 判断是否压缩、限流或收尾。没有固定工作流，只有可用工具与终止条件。

  1. 组装。系统提示、任务、工作区状态、三层记忆的检索结果、近期工具结果。
  2. 决策。模型选择直接回答，或调用一个工具；不允许一次生成一大段脚本绕开工具注册表。
  3. 执行。工具分发到具体实现；需要审批的走 HITL，被拒绝则把拒绝原因回填给模型。
  4. 回填。结果按策略截断或摘要，大对象落盘，只把可读部分放回上下文。
  5. 收尾。达到轮数上限、模型给出最终回答、任务被取消，或连续无进展。
轮数上限

主循环 40 轮，子代理 20 轮。上限不是性能参数，是失败可见性参数：与其让 agent 无限试错，不如在边界处停住，把未完成的活留在「待验」并说明卡在哪。

04工具注册与权限

模型只能看到注册表里的工具。当前有 27 个绑定，覆盖论文检索、PDF 下载、按节阅读、笔记、领域、审批与上下文管理。run_bash 存在，但不在模型工具表里，只能经 HITL 审批触发。

层例子默认可见边界
论文get_papers、paper_pdf_download、read_paper_section是全文只从 arXiv 来
判断save_item是只能写候选态
扫描关键词通道、前向 / 后向引用链是每次运行写回执
上下文压缩、记忆检索、todo 更新是两档压缩阈值
系统run_bash否仅 HITL，不进模型表

判断工具另有一条证据约束：located=true 时必须带一段逐字来自所述节的引句（12–300 字符、连续一段），发表与修改都按归一化规则对节正文校验；校验不过整条拒绝，并给模型可读的改法。领域会话里 save_note / save_item 写到的论文会自动挂进当前领域（role=read，已有角色不动）——否则论文只落在全局论文库，领域论文库与领域笔记里都看不到。

权限不是靠提示词约束，而是靠注册表与审批层。模型不知道 run_bash 存在，就不会试图「找个办法执行命令」。这是把安全边界放在代码而不是语气里。

05三层记忆与两档压缩

「记得什么」比「上下文多长」更重要。三层记忆各管一件事：

01 · NOTES

笔记检索

Chroma 向量索引，按任务语义召回组里已有的笔记与判断。

02 · PAPERS

论文元数据

标题、作者、标识、领域归属与阅读状态，决定「读没读过」。

03 · CONTEXT

上下文

当前任务的工具结果与轨迹，按 128K 窗口管理。

上下文不是无限堆叠。70% 与 90% 是两档压缩阈值：70% 开始折叠早期工具结果，保留结论与出处；90% 强制压缩并丢弃可重新获取的中间产物。压缩后的内容仍然要能回答「依据是什么」，否则宁可让任务失败。

可重取原则

能重新下载的 PDF、能重新调用的接口结果，可以丢；判断、引句、节锚点不能丢。压缩策略按「可重取性」而不是「长度」排序。

06失败与边界

系统假设失败是常态：网络会超时，OpenAlex 会 429，PDF 会缺页，模型会调错工具。架构的目标不是避免失败，而是让失败有位置可落。

  • 通道失败写 channel_runs，记 ok / fail / skip，清单照常交付。
  • 工具失败回填给模型，允许换路径；重复失败计入「无进展」判断。
  • 任务失败停在待验，附失败原因与最后一步轨迹，不静默重试到天荒地老。
  • 进程重启时 queued 任务自动恢复；运行中的任务标记为中断，等人决定是否重跑。

这些机制在 行为治理与失败可见性里展开；架构图与部署拓扑在 系统上下文与容器里展开。

07从哪里继续读

如果你关心「它为什么这样组织」，下一步读系统上下文与容器；如果你关心「它失败时怎么办」，读行为治理与失败可见性；如果你关心「人怎么参与」，读一个人，一周，从交活到组会。

  • 代码边界 core 不依赖 backend
  • 任务边界 落库再跑，不靠内存
  • 工具边界 模型只见注册表
  • 失败边界 停在待验，不静默吞掉
